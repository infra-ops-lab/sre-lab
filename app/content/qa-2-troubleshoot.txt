## Kubernetes troubleshooting | K8s
Q: A pod is in CrashLoopBackOff. How do you debug it?
A: The container starts and exits again and again; the kubelet backs off (10 s, 20 s… up to 5 min).
- `kubectl describe pod <p>`: look at **Last State: Terminated, Reason, Exit Code**, and Events.
- `kubectl logs <p> --previous`: logs of the crashed run (the current one may be empty).
- **Exit code meaning:** 1 = app error; 137 = SIGKILL (often OOMKilled); 139 = segfault; 143 = SIGTERM.
- Common causes: bad config or missing env/secret, app can't reach a dependency at start, wrong command/entrypoint, **liveness probe too aggressive** (kills a slow-starting app), OOM.
- If logs are empty: `kubectl debug -it <p> --copy-to=dbg --container=app -- sh` or override the command to `sleep` and start the app by hand.
F: Logs are empty and exit code is 0. What does that mean? (The process finished normally. A job-like command in a Deployment, or the main process daemonised and exited.)

Q: A pod is stuck in Pending. What do you check?
A: Pending = not scheduled yet (or volumes not ready). `kubectl describe pod` → **Events** says why:
- **Insufficient cpu/memory:** requests too big for any node; check `kubectl describe node` allocatable vs requested; Cluster Autoscaler should add a node (check its logs if it doesn't).
- **Taints / nodeSelector / affinity** don't match any node.
- **PVC not bound:** no matching PV, wrong StorageClass, or WaitForFirstConsumer with a zone mismatch.
- **Too many pods** on the node (`max-pods`), or a ResourceQuota in the namespace blocks it (that shows as a failed create on the ReplicaSet, not Pending).
F: Requests are tiny but it's still Pending with "Insufficient cpu". Why? (Requests are summed per node, not actual usage. Nodes are full of requested-but-unused CPU.)

Q: A container is OOMKilled. How do you investigate and fix it?
A: The container used more memory than its **limit**, so the kernel's cgroup OOM killer killed it (exit code 137, reason OOMKilled).
- Check usage trend: `container_memory_working_set_bytes` against the limit. Steady growth = leak; spikes = load or big requests.
- Check the runtime: JVM heap must be smaller than the container limit (`-XX:MaxRAMPercentage`), same for Node.js `--max-old-space-size`.
- Fix: raise the limit if the usage is legitimate; fix the leak; limit concurrency. Set **requests = realistic usage** so the scheduler places it well.
- Node-level OOM (not cgroup) is different: the node ran out of memory; kubelet evicts pods by QoS (BestEffort first) or the kernel kills processes. Look at `dmesg` and node events.
F: What are the QoS classes and why do they matter? (Guaranteed: requests = limits for all containers; Burstable: some requests set; BestEffort: none. Under node pressure, BestEffort is evicted first, Guaranteed last.)

Q: Should you set CPU limits on pods?
A: It's a known debate; give both sides and a position.
- **CPU limits cause throttling** (CFS quota): a pod can be throttled even when the node has idle CPU, which hurts latency (look at `container_cpu_cfs_throttled_periods_total`).
- Many teams set **CPU requests (for scheduling and fair share) but no CPU limits** for latency-sensitive services; CPU is compressible, so sharing spare CPU is safe.
- **Memory is different:** always set memory limits (memory isn't compressible; without a limit one pod can starve the node).
- Keep limits for noisy or untrusted multi-tenant workloads, or use LimitRange defaults.
F: p99 latency is bad but CPU usage is only 40% of the limit. What do you suspect? (Throttling: usage is averaged; bursts within each 100 ms period hit the quota.)

Q: A Service isn't reachable. Pods are Running. Walk me through it.
A: Follow the path from the client to the pod:
- **Endpoints:** `kubectl get endpointslices -l kubernetes.io/service-name=<svc>`. Empty = selector doesn't match pod labels, or pods aren't Ready (readiness probe failing).
- **Ports:** Service `targetPort` matches the container port the app actually listens on? App listening on 127.0.0.1 instead of 0.0.0.0?
- **From inside:** `kubectl run tmp --rm -it --image=nicolaka/netshoot -- bash`, then `curl svc.ns.svc.cluster.local:port` and `curl <podIP>:port` directly. If pod IP works but Service doesn't: kube-proxy/iptables/IPVS or the CNI.
- **NetworkPolicy:** a default-deny policy blocking ingress or egress (including DNS on port 53).
- **DNS:** does the name resolve? (see the DNS question)
F: Pod IP works from the same node but not from other nodes. Where's the problem? (CNI overlay/routing between nodes: VXLAN port blocked, MTU, BGP routes.)

Q: DNS resolution fails intermittently inside pods. How do you debug it?
A:
- Test from a debug pod: `nslookup kubernetes.default`, `dig svc.ns.svc.cluster.local`. Check `/etc/resolv.conf` (nameserver = cluster DNS IP, `ndots:5`).
- CoreDNS health: pods Running? Logs (enable the `log` plugin briefly)? CPU throttled? Enough replicas for the query rate?
- **ndots:5** makes external names try 4-5 search domains first, multiplying queries. Use FQDNs with a trailing dot or lower ndots for heavy clients.
- **conntrack races on UDP** (the classic Linux bug causing 5 s timeouts) → NodeLocal DNSCache fixes it and cuts latency.
- Check upstream DNS (CoreDNS `forward`) and NetworkPolicies allowing UDP/TCP 53 to kube-system.
F: Why do DNS timeouts often show up as exactly 5 seconds? (The resolver's default timeout before retry.)

Q: A node goes NotReady. What happens to its pods? Deployment vs StatefulSet?
A:
- The node controller marks it NotReady after the kubelet stops reporting (`node-monitor-grace-period`, ~40-50 s) and taints it `node.kubernetes.io/unreachable` or `not-ready`.
- Pods tolerate those taints for **300 s by default**, then get evicted (marked for deletion).
- **Deployment pods:** the ReplicaSet creates replacements on healthy nodes right away; the old ones stay "Terminating" until the node returns.
- **StatefulSet pods are NOT replaced automatically**: StatefulSets guarantee at most one pod per identity, and Kubernetes can't know the old pod is really dead (could be a network partition, still writing to the volume). They stay Terminating/Unknown.
- To recover: confirm the node is really down, then delete the Node object, force-delete the pod, or use the **non-graceful node shutdown** taint `node.kubernetes.io/out-of-service`. RWO volumes must detach first.
- Debug the node: `kubectl describe node` (conditions: MemoryPressure, DiskPressure, PIDPressure), then on the node `systemctl status kubelet containerd`, `journalctl -u kubelet`, disk space, certificate expiry, network to the API server.
F: Why is force-deleting a StatefulSet pod dangerous? (Split brain: two pods with the same identity writing the same data.)

Q: A pod is stuck in Terminating. What do you do?
A:
- `kubectl get pod -o yaml`: look for **finalizers** (something must clean up first) and `deletionTimestamp`.
- Node unreachable? The kubelet can't confirm the stop (see NotReady question).
- App ignores SIGTERM and `terminationGracePeriodSeconds` is long; or a preStop hook hangs.
- Volume detach stuck (CSI driver).
- Last resort: `kubectl delete pod --grace-period=0 --force`, only after you understand why (dangerous for StatefulSets).
F: A whole namespace is stuck Terminating. Why? (A resource inside has a finalizer whose controller is gone, often a CRD or an API service that's down. Check `kubectl get apiservice` for unavailable ones.)

Q: A rollout is stuck. `kubectl rollout status` never finishes. What do you check?
A:
- `kubectl rollout status` / `describe deploy`: condition **Progressing=False, ProgressDeadlineExceeded**.
- New pods failing: CrashLoop, ImagePullBackOff (wrong tag, registry auth, rate limit), readiness probe never passes.
- Not enough capacity for surge pods (`maxSurge`) → Pending; or a **PodDisruptionBudget** blocking during node drain.
- Admission webhook (e.g., a policy engine) rejecting the new ReplicaSet's pods; check ReplicaSet events.
- Fix: `kubectl rollout undo deploy/x`, then debug the new version separately.
F: How do you make bad rollouts stop automatically? (Readiness probes + progressDeadlineSeconds; canary with automated analysis in Argo Rollouts/Flagger.)

Q: Users get 502/504 errors through the ingress. How do you find the cause?
A:
- **502 Bad Gateway:** the ingress couldn't get a valid response from the backend: pod not ready but still in endpoints, app crashed, wrong port, or the app closed a keep-alive connection the proxy reused (set the app's keep-alive timeout higher than the proxy's).
- **504 Gateway Timeout:** backend too slow for the proxy timeout: slow DB, overloaded pods, too-small timeouts.
- **During deploys only:** pods killed before endpoints update → add a `preStop` sleep (5-10 s) and graceful shutdown so in-flight requests finish.
- Check ingress controller logs (upstream status and response time per request), backend RED metrics, endpoints churn.
F: 502s only appear during rolling deploys. Fix? (preStop sleep + handle SIGTERM gracefully + readiness fails first.)

Q: The control plane is slow: kubectl takes seconds. What do you check?
A:
- **API server:** request latency and rate by verb/resource (`apiserver_request_duration_seconds`), 429s (API Priority and Fairness throttling), a client doing huge LIST calls without pagination or watching everything.
- **etcd:** disk fsync latency (`etcd_disk_wal_fsync_duration_seconds` p99 should be < 10 ms; etcd needs fast SSDs), leader changes, DB size near the quota (default 2 GB), too many objects (e.g., thousands of old Events, ReplicaSets, Secrets).
- **Admission webhooks** that are slow or timing out add latency to every write.
- Fixes: defragment etcd, compact, clean old objects, fix the noisy client, faster disks, more API server replicas.
F: What happens if etcd loses quorum? (Cluster becomes read-only at best, no writes; existing pods keep running but nothing can change.)

Q: Cluster certificates expired. What breaks and how do you fix it?
A:
- kubeadm-issued certs last **1 year**; when they expire, kubectl, kubelet → API server, and API server → etcd connections fail with x509 errors. Running pods often keep working, but nothing can be managed.
- Check: `kubeadm certs check-expiration`; `openssl x509 -enddate -noout -in /etc/kubernetes/pki/apiserver.crt`.
- Fix: `kubeadm certs renew all` on each control-plane node, restart the static control-plane pods, update admin kubeconfig. Kubelet client certs rotate automatically if rotation is on.
- Prevent: kubeadm renews certs on every upgrade (so upgrading at least yearly avoids this); alert on expiry 30 days before (e.g., x509-certificate-exporter).
F: How do you detect cert expiry across 1,000+ clusters before it bites?

Q: A node has DiskPressure and pods are being evicted. What do you do?
A:
- Kubelet evicts pods when `nodefs` or `imagefs` free space drops below the eviction thresholds (e.g., 10% / 15%).
- Find what's using disk: container images (`crictl images`, `crictl rmi --prune`), container logs (`/var/log/pods`), emptyDir volumes, a pod writing huge files.
- Kubelet garbage-collects images at `imageGCHighThresholdPercent`; check it's working.
- Fix: log rotation (containerd `max-size`), `ephemeral-storage` requests and limits on pods, bigger disks, alert at 80%.
F: Disk is full but `du` shows much less used than `df`. Why? (Deleted files still held open by a process. Find with `lsof +L1`; restart that process.)

Q: HPA isn't scaling the deployment. Why?
A:
- `kubectl describe hpa`: conditions and events. "unable to get metrics" = metrics-server (or the Prometheus adapter) not working.
- **Pods have no CPU requests**: HPA CPU % is calculated against requests; without requests it can't compute.
- Already at `maxReplicas`; or new pods Pending because there's no node capacity (that's the Cluster Autoscaler's job).
- Stabilization windows (scale-down default 300 s) and tolerance (10%) make it look slow.
- The metric isn't the bottleneck (CPU low but latency high because of a DB or I/O): scale on a better metric (RPS, queue length) via custom/external metrics or KEDA.
F: HPA vs VPA vs Cluster Autoscaler vs Karpenter? (HPA: more pods. VPA: bigger requests per pod. CA: more nodes from fixed node groups. Karpenter: picks and creates the right node type on demand, faster, bin-packs. Don't run HPA and VPA on the same CPU metric.)

Q: ImagePullBackOff: causes?
A:
- Wrong image name or tag (typo, tag deleted).
- Private registry without `imagePullSecrets`, or expired credentials.
- Registry rate limit (Docker Hub), registry down, or the node can't reach it (proxy, DNS, firewall, air-gapped site without a mirror).
- Architecture mismatch (arm64 vs amd64) shows as exec format error after the pull, not pull errors.
- Check: `kubectl describe pod` events; on the node `crictl pull <image>` to see the exact error.
F: How do you run Kubernetes in an air-gapped site? (Local registry mirror like Harbor, containerd mirror config, pre-seeded images, signed bundles.)

Q: How do you debug a pod that has no shell (distroless image)?
A:
- `kubectl debug -it <pod> --image=nicolaka/netshoot --target=<container>`: adds an **ephemeral container** that shares the process namespace, so you can see its processes and network.
- `kubectl debug node/<node> -it --image=ubuntu`: a pod on the node with the host filesystem at `/host`.
- `kubectl port-forward` to test the app directly; `kubectl exec` only works if the image has the binary.
F: How do you capture packets for a single pod? (Ephemeral container with tcpdump, sharing the pod's network namespace.)

## Linux troubleshooting | Linux
Q: A Linux server is "slow". How do you investigate?
A: Use USE (utilization, saturation, errors) per resource, with the first-60-seconds checklist:
- `uptime`: load averages trend (1/5/15 min).
- `dmesg -T | tail`: OOM kills, disk errors, NIC resets.
- `vmstat 1`: run queue `r` (CPU saturation), `si/so` swapping, `wa` I/O wait.
- `mpstat -P ALL 1`: one core at 100% (single-threaded bottleneck)?
- `pidstat 1`: which process uses CPU.
- `iostat -xz 1`: disk `%util`, `await` (latency), queue size.
- `free -m`: available memory (not "free": cache is reclaimable).
- `sar -n DEV 1`, `sar -n TCP,ETCP 1`: network throughput, retransmits.
- `top`/`htop` to confirm. Then go deep on the bottleneck (perf, strace).
F: Load average is 40 on an 8-core box but CPU is 20% busy. What's happening? (Linux load includes tasks in uninterruptible sleep (D state), usually waiting on disk or NFS. Check `iostat` and `ps -eo state,pid,cmd | grep ^D`.)

Q: What is a process in D state, and why can't you kill it?
A: D = **uninterruptible sleep**: the process is inside the kernel waiting for I/O (disk, NFS, a hung storage device) and doesn't handle signals until the I/O returns.
- `kill -9` doesn't work until the I/O completes.
- Causes: slow or failed disk, NFS server unreachable, storage driver bug.
- Find what it waits on: `cat /proc/<pid>/stack` (as root), `ps -eo pid,state,wchan:30,cmd`.
- Fix the storage or network path; sometimes only a reboot clears it.
F: How does D state affect load average and alerts?

Q: How does the Linux OOM killer work?
A:
- When the kernel can't reclaim memory, it picks a process by `oom_score` (mostly by memory use, adjusted by `oom_score_adj`) and kills it.
- Logs in `dmesg` / `journalctl -k`: "Out of memory: Killed process …".
- In containers, the **cgroup** limit triggers the OOM killer inside that cgroup only.
- Protect critical processes with a negative `oom_score_adj` (kubelet sets these by QoS class).
- `free` shows "available" memory; page cache is reclaimable and is not a problem by itself.
F: Memory "used" is 95% but the app is fine. Problem? (Probably not: most is page cache. Check "available" and swap/major page faults.)

Q: "Too many open files" errors. What do you do?
A:
- Each process has a file-descriptor limit (`ulimit -n`, soft/hard; for services `LimitNOFILE` in systemd). Sockets count as files.
- Check current use: `ls /proc/<pid>/fd | wc -l`, `cat /proc/<pid>/limits`; system-wide `cat /proc/sys/fs/file-nr` vs `fs.file-max`.
- Leak (count keeps growing) → fix the app (unclosed connections/files). Legit high concurrency → raise the limit.
F: You raised `ulimit` in your shell but the service still fails. Why? (systemd services don't read shell limits; set `LimitNOFILE` in the unit and restart.)

Q: Many connections in TIME_WAIT or CLOSE_WAIT. What does each mean?
A:
- **TIME_WAIT:** normal; the side that closes first waits 2×MSL (60 s on Linux) so late packets don't corrupt new connections. Huge numbers mean lots of short connections → use keep-alive/connection pooling; for outgoing connections ephemeral ports can run out (`net.ipv4.ip_local_port_range`, `tcp_tw_reuse`).
- **CLOSE_WAIT:** the remote side closed, but **your application never called close()**. That's an app bug (connection leak), not a kernel tuning issue.
- Check with `ss -tan state time-wait | wc -l` and `ss -tanp state close-wait`.
F: Which one is a bug in your code? (CLOSE_WAIT.)

Q: How do you use strace and when?
A: strace shows the system calls a process makes. Use it when a process hangs, fails without a useful log, or is slow and you don't know why.
- `strace -p <pid> -f -tt -T`: attach to a running process, follow threads, timestamps, time per call.
- `strace -c -p <pid>`: summary of which syscalls take the time.
- `strace -e trace=network,file cmd`: only network/file calls. You'll see e.g. a config file it can't open, a connect() hanging to a dead IP, a slow DNS lookup.
- Overhead is high: careful on busy production processes. `perf` or eBPF tools (bcc/bpftrace) are lighter.
F: A process is stuck. strace shows it blocked in `futex()`. What does that mean? (Waiting on a lock/another thread. Look at thread stacks with gdb/jstack, not the kernel.)

Q: How do you use tcpdump to debug a network problem?
A:
- `tcpdump -i any -nn host 10.0.0.5 and port 443 -w cap.pcap`, then open in Wireshark.
- What to look for: SYN with no SYN-ACK (firewall/route/nothing listening), RST (port closed or app rejects), retransmissions (packet loss), TLS handshake alert, slow server response (time between request and reply), DNS queries with no answer.
- In Kubernetes: run it in the pod's network namespace (ephemeral debug container), or on the node on the right interface (veth/cni0/vxlan).
F: You see the request leave the client but the server never sees it. Where do you look? (Anything in between: security groups/firewalls, NAT/conntrack, routing, MTU, the LB.)

Q: High iowait. How do you find the cause?
A:
- `iostat -xz 1`: which device; `%util` near 100%, high `await`, growing `aqu-sz` = disk saturated.
- `iotop` or `pidstat -d 1`: which process does the I/O.
- Look for: swapping (`vmstat si/so`), a backup or log job, a DB doing full scans, a noisy neighbour on shared storage, a failing disk (`dmesg`, `smartctl`).
F: iowait is high but the disk isn't busy. Possible? (Yes: network storage (NFS/iSCSI/Ceph) latency, or a single slow device in the path.)

Q: What happens when you type `curl https://example.com`? Go deep.
A:
- **DNS:** `/etc/hosts`, then resolvers in `/etc/resolv.conf` → recursive resolver → root → TLD → authoritative; result cached by TTL.
- **TCP:** 3-way handshake SYN, SYN-ACK, ACK to port 443 (through routing, NAT, firewalls, load balancer).
- **TLS 1.3:** ClientHello (SNI, supported ciphers, key share) → ServerHello + certificate chain + finished; client verifies the chain to a trusted root, hostname and validity dates; keys derived; 1 round trip.
- **HTTP:** GET request with Host header; LB/proxy routes to a backend; response with status, headers, body; connection kept alive.
- **Close:** FIN/ACK; TIME_WAIT on the closing side.
F: Where could each step fail, and what would you see? (DNS: "could not resolve"; TCP: timeout or refused; TLS: certificate errors; HTTP: 4xx/5xx.)

Q: What is a zombie process? An orphan?
A:
- **Zombie (Z):** finished, but its parent hasn't read its exit status (`wait()`). Uses no memory, only a PID slot. Many zombies = parent bug; killing the zombie does nothing; kill/fix the parent.
- **Orphan:** parent died; it gets re-parented to PID 1 (or a subreaper), which reaps it.
- In containers, PID 1 is your app; if it doesn't reap children you get zombies → use `tini`/`--init` or `shareProcessNamespace`.
F: Why can zombies eventually take down a node? (PID exhaustion; Kubernetes has PIDPressure and `podPidsLimit` for this.)

Q: Disk shows free space but you can't create files. Why?
A: **Inodes are exhausted.** Every file uses an inode; millions of tiny files (cache, sessions, mail queue) use them all.
- Check: `df -i`.
- Find: `find / -xdev -type d -size +1M` or count files per directory.
- Fix: delete the small files, fix the app producing them; for new filesystems choose inode density (or XFS, which allocates dynamically).
F: Two other reasons you can't write: read-only remount after disk errors (`dmesg`), quota limits.

## Networking basics | Net
Q: L4 vs L7 load balancing: differences and when to use which?
A:
- **L4 (TCP/UDP):** routes by IP and port; doesn't look inside; very fast; passes TLS through. E.g., AWS NLB, MetalLB, IPVS.
- **L7 (HTTP):** reads headers, paths, cookies; can route `/api` vs `/web`, do retries, rate limits, auth, header rewrites, canary by header; terminates TLS. E.g., ALB, NGINX/Envoy ingress, Gateway API.
- L7 costs more CPU and adds a hop, but gives you much better observability (per-route status codes and latency).
F: Where would you terminate TLS, and why?

Q: How do you debug a TLS/certificate error?
A:
- `openssl s_client -connect host:443 -servername host -showcerts`: see the chain the server sends, verify result, expiry.
- Common causes: **expired cert**; **missing intermediate** (works in browsers that cache it, fails in curl/Java); hostname mismatch (SAN doesn't include it); client doesn't trust the CA (private CA not in the trust store); clock skew on the client; SNI missing so the wrong cert is served.
- For mTLS: client cert not sent, signed by a CA the server doesn't trust, or wrong key usage.
F: It works in the browser but fails from the Java service. Most likely? (Missing intermediate certificate or a different trust store.)

Q: Large requests hang but small ones work. What could it be?
A: Classic **MTU / fragmentation** problem.
- Overlays (VXLAN adds ~50 bytes, IPsec/WireGuard more) reduce the usable MTU; if ICMP "fragmentation needed" is blocked, Path MTU Discovery fails and big packets silently drop (black hole).
- Test: `ping -M do -s 1472 host` (1472 + 28 = 1500), lower until it works.
- Fix: set the CNI/interface MTU correctly (e.g., 1450 for VXLAN on 1500), allow ICMP type 3 code 4, or MSS clamping.
F: Why does the TLS handshake hang but TCP connect works? (Server certificate chain is a big packet. Same MTU black hole.)

Q: What is conntrack and how can it cause outages?
A: Netfilter's connection-tracking table: every NATed/tracked connection (kube-proxy iptables mode uses it) gets an entry.
- When the table fills (`nf_conntrack_max`), new connections are **dropped**; `dmesg` shows "nf_conntrack: table full, dropping packet".
- Check: `conntrack -C` vs `sysctl net.netfilter.nf_conntrack_max`.
- Fix: raise the max (memory cost), shorten timeouts, reduce short-lived connections (keep-alive), NodeLocal DNSCache for UDP DNS.
F: Why are UDP DNS lookups especially affected?

Q: A DNS change was made but some users still go to the old IP. Why?
A:
- **TTL caching** at every layer: recursive resolvers, OS, language runtimes (old JVMs cache forever by default), browsers.
- Before a planned change: lower the TTL (e.g., to 60 s) at least one old-TTL period in advance, then change, then raise it again.
- Negative caching (NXDOMAIN cached by SOA minimum) for newly created records.
F: How would you migrate traffic between two data centres using DNS safely? (Weighted records, low TTL, health checks, watch both sides.)
