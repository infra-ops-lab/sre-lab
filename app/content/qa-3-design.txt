## Safe releases | Release
Q: Rolling update vs blue-green vs canary: compare them.
A:
- **Rolling:** replace pods a few at a time (`maxSurge`/`maxUnavailable`). Cheap, default in Kubernetes. Old and new versions run together; rollback = another rollout (minutes).
- **Blue-green:** run the full new version (green) beside the old (blue); switch all traffic at once (LB/Service selector). Instant rollback by switching back. Costs 2x capacity during the switch; everyone gets the new version at once.
- **Canary:** send a small % of traffic (1% → 5% → 25% → 100%) to the new version, compare its metrics with the old, promote or roll back automatically. Smallest blast radius; needs good metrics and traffic splitting (service mesh, ingress, Argo Rollouts/Flagger).
- Choose by risk and cost: canary for user-facing services, blue-green when versions can't coexist or you need instant switch-back, rolling for low-risk internal services.
F: What do you compare during a canary, and how long do you wait? (Error rate, latency p99, saturation of the canary vs the baseline; long enough to see real traffic, e.g. 10-30 min per step, longer for slow-burn issues like memory leaks.)

Q: How do you roll out a change to 1,000+ clusters safely?
A: Treat the fleet like a canary.
- **Rings/waves:** lab → internal/pilot sites → 1% → 10% → 50% → 100%, with a bake time between waves.
- **Health gates:** automated checks after each wave (nodes Ready, pods healthy, key SLIs, no new alerts); stop automatically if the failure rate passes a threshold (e.g., more than 2% of clusters fail).
- **Rollback plan** tested before the rollout; for things that can't roll back (etcd, schema), have a restore procedure.
- **Diversity in early waves:** include different hardware, versions and site types so problems show up early.
- Freeze windows (peak business periods like holiday season for retail).
F: Wave 3 has a 5% failure rate. What do you do? (Halt, keep the failed sites safe, compare failed vs healthy ones to find the common factor, fix, resume.)

Q: How do you deploy a database schema change without downtime?
A: **Expand and contract** (parallel change):
- **Expand:** add the new column/table (backwards-compatible); old code keeps working.
- **Migrate:** deploy code that writes both old and new, backfill old rows in batches.
- **Switch reads** to the new column.
- **Contract:** after all code uses the new shape (and rollback is no longer needed), remove the old column.
- Never rename or drop in the same release as the code change; that makes rollback impossible.
F: Why is "rollback" dangerous after a migration?

Q: Feature flags: how do they help reliability?
A:
- Separate **deploy** (code is on servers) from **release** (users see it). Turn features on for 1% of users, internal staff or one region first.
- Instant kill switch without a redeploy.
- Risks: flag debt (old flags never removed), untested flag combinations, the flag service itself becomes a dependency (cache flags locally, default safely).
F: The flag service is down. What should the app do?

Q: Roll back or roll forward?
A:
- **Default: roll back** when the last change is the likely cause and rollback is safe. It's tested, fast and known-good.
- **Roll forward** when rollback is risky or impossible (data migrated, external API contract changed) or the fix is tiny and obvious.
- Decide before the incident: every change should have a documented rollback path.
F: What if you don't know which of 5 changes caused it?

## Capacity and scaling | Capacity
Q: How do you do capacity planning for a service?
A:
- **Measure demand:** peak QPS, growth trend, seasonality (e.g., retail holiday season = 3-5x).
- **Measure supply:** load test to find the throughput per instance at the SLO latency (not at 100% CPU), and the real bottleneck (CPU, memory, DB connections, I/O).
- **Headroom:** plan for peak + growth + **N+1 or N+2** (survive losing a node or a zone). Typical: run at 50-70% of tested capacity.
- **Lead time:** how long to get more (minutes for cloud autoscaling, months for bare metal) → order ahead.
- Review quarterly; alert on trend ("80% of capacity in 3 weeks").
F: How do you size for losing a whole availability zone with 3 zones? (Each zone must carry 50% of peak, so you run at about 2/3 of capacity normally.)

Q: HPA, VPA, Cluster Autoscaler and Karpenter: explain each.
A:
- **HPA:** adds/removes pod replicas based on metrics (CPU % of requests, memory, custom metrics like RPS or queue length).
- **VPA:** recommends or sets CPU/memory **requests** per pod based on history; recreates pods to apply (in-place resize is newer). Good for right-sizing.
- **Cluster Autoscaler:** adds nodes when pods are Pending for lack of resources, removes underused nodes; works with fixed node groups.
- **Karpenter:** provisions the right instance type directly for pending pods (no fixed node groups), faster, consolidates and bin-packs to cut cost.
- **KEDA:** event-driven scaling (Kafka lag, queue depth), including scale to zero.
F: Why not use HPA and VPA together on CPU? (They fight: VPA raises requests, HPA's CPU % drops, it scales in, and so on.)

Q: How do you load test a service properly?
A:
- Define the goal: max throughput at the SLO latency, or behaviour at 2x peak, or a soak test for leaks.
- Realistic traffic mix and data (not one URL); test from outside the cluster; ramp up gradually.
- Tools: k6, Locust, JMeter, vegeta.
- Watch: latency percentiles, errors, saturation of every layer (app, DB, cache, LB); find the first bottleneck, fix, repeat.
- Run it in an environment like production, or carefully in production off-peak with protections.
F: Your test shows 5,000 RPS per pod. Will production get that? (Probably not: cache warmth, data size, dependencies, noisy neighbours. Keep a margin.)

Q: Cost: how do you reduce Kubernetes overprovisioning?
A:
- Measure: requested vs actually used CPU/memory per namespace/team (Kubecost/OpenCost, Prometheus). Typical clusters use 20-40% of requested CPU.
- Right-size requests from p95 usage history (VPA recommendations).
- Bin-packing and consolidation (Karpenter), spot/preemptible nodes for stateless workloads, scale down non-prod at night.
- Show each team its cost (showback) so owners care.
F: How do you right-size without hurting reliability? (Change gradually, watch OOM kills and throttling, keep headroom on critical services.)

## Resilience patterns and chaos | Resilience
Q: Explain timeouts, retries, exponential backoff and jitter.
A:
- **Timeouts:** every network call needs one, shorter than the caller's own timeout (propagate deadlines). No timeout = threads pile up and the caller dies too.
- **Retries:** only for transient errors and **idempotent** operations; limit attempts (e.g., 2-3) and use a **retry budget** (e.g., max 10% extra traffic).
- **Exponential backoff:** wait 100 ms, 200 ms, 400 ms… so a struggling service gets room to recover.
- **Jitter:** randomise the wait so thousands of clients don't retry at the same instant (thundering herd).
- Retry at **one** layer only; retries at every layer multiply (3 layers × 3 retries = 27x load).
F: How can retries turn a small blip into a full outage? (Retry storm: overloaded service gets 3x traffic exactly when it's weakest.)

Q: What is a circuit breaker?
A: A wrapper around calls to a dependency that **stops calling it when it keeps failing**.
- **Closed:** normal; count failures. **Open:** after too many failures, fail fast immediately (or serve a fallback) for a cool-down period. **Half-open:** let a few test calls through; close if they succeed.
- Protects your threads/connections from a dead dependency and gives it time to recover.
- Implemented in libraries (resilience4j) or the service mesh (Envoy outlier detection).
F: What fallback would you serve when the recommendations service is down? (Graceful degradation: a generic list, cached results, or hide the widget.)

Q: What is a cascading failure, and how do you prevent it?
A: One component overloads or fails, its load moves to others, they overload too, and the failure spreads.
- Typical trigger: one replica dies → the rest get more load → they slow down → timeouts → retries add load → they die.
- Prevent: **load shedding** (reject excess early with 429/503, keep serving the rest), **rate limits**, timeouts and retry budgets, circuit breakers, autoscaling with headroom, **bulkheads** (separate pools per dependency/tenant), and capacity for N+1.
F: What's the difference between load shedding and rate limiting? (Rate limiting caps a client; load shedding protects the server based on its own overload.)

Q: What is graceful degradation? Give examples.
A: Keep the core user journey working while non-critical parts are down or slow.
- E-commerce: checkout works even if recommendations or reviews are down.
- Serve stale cache when the DB is slow; read-only mode when writes fail.
- Lower quality under load (smaller images, fewer results).
- Design it in advance: mark which dependencies are critical and which are optional.
F: How do you test that degradation actually works? (Chaos experiments that kill the optional dependency.)

Q: What is chaos engineering and how would you start it safely?
A: Running controlled experiments that inject failure to prove the system handles it, before a real incident does.
- **Steps:** define steady state (an SLI) → hypothesis ("if one pod of service X dies, the SLI stays within SLO") → inject (kill pod, add 300 ms latency, drop a node, fill disk, block a dependency) → observe → fix what broke.
- **Start small:** staging first, then production with a small blast radius, business hours, an abort button, everyone informed.
- Tools: Chaos Mesh, LitmusChaos, AWS FIS, Gremlin. **Game days** to practise incident response too.
F: What's the first experiment you'd run on a Kubernetes platform? (Kill a node and check pods reschedule, PDBs hold, and the SLI stays green.)

Q: What does idempotency mean and why does it matter for reliability?
A: An operation is idempotent if doing it twice has the same effect as doing it once (PUT, DELETE, "set X to 5"; not "add 5 to X").
- It makes **retries safe**: a timeout doesn't tell you if the request succeeded.
- For non-idempotent operations (payments), use **idempotency keys**: the client sends a unique key, the server stores results by key and returns the same result on retry.
F: A payment request timed out. Should the client retry?

## Cluster and system design | Design
Q: Design a highly available Kubernetes control plane.
A:
- **3 or 5 control-plane nodes** across failure domains (zones/racks); etcd quorum = (n/2)+1, so 3 nodes tolerate 1 failure, 5 tolerate 2. Never 2 or 4 (no extra tolerance).
- **etcd:** stacked (on the control-plane nodes, simpler) or external (separate nodes, more isolation); fast SSDs; low-latency network between members.
- **API server** behind a load balancer (or a VIP with keepalived/kube-vip on bare metal); all kubelets and clients use the LB address.
- Scheduler and controller-manager run active-passive via leader election.
- Backups: scheduled etcd snapshots off-cluster; tested restores.
- Monitoring of etcd (fsync latency, leader changes, DB size) and certificate expiry.
F: Why not spread 3 etcd nodes across 2 data centres? (One DC holds 2 members; if it fails you lose quorum. Use 3 sites or keep etcd in one site.)

Q: How do you back up and restore etcd? What's the RTO?
A:
- Backup: `etcdctl snapshot save` on a schedule (e.g., hourly), copied off the node to object storage; also back up the PKI (`/etc/kubernetes/pki`).
- Restore: stop the API servers, `etcdutl snapshot restore` into a new data dir on each member with the new cluster settings, start etcd, then the control plane.
- You lose changes since the snapshot (RPO = snapshot interval). Objects created after it disappear; controllers reconcile running state.
- Also consider **Velero** for namespaced resources plus persistent volumes, which is more useful for app-level restore.
- **Test restores regularly.** An untested backup is not a backup.
F: When would you restore etcd vs rebuild the cluster from Git (GitOps)? (With GitOps, rebuilding from Git is often faster and cleaner for stateless workloads. etcd restore matters for state not in Git.)

Q: Active-active vs active-passive multi-region: trade-offs?
A:
- **Active-passive:** one region serves; the other is standby (warm or cold). Simpler data consistency; failover takes minutes and is risky if rarely tested; standby capacity is idle cost.
- **Active-active:** both regions serve traffic (GeoDNS/anycast). Survives region loss with little downtime and uses all capacity; hard part is **data**: multi-region writes need conflict handling or a globally distributed DB, and latency between regions.
- Decide by RTO/RPO needs, data model and budget. Many teams do active-active for stateless tiers and a single primary DB with a replica in the other region.
F: How do you make sure failover actually works? (Regular failover drills, automated health checks, run real traffic in the secondary.)

Q: Two clusters: an app cluster and a data cluster. How does traffic get from the app to the data layer, securely and reliably?
A: Say the layers explicitly:
- **Network path:** same VPC (simple), VPC peering or Transit Gateway (routed, CIDRs must not overlap), or **PrivateLink / private endpoint** (one-way, service-level, no CIDR clash, best isolation). On-prem: routed networks or a dedicated link.
- **Entry to the data cluster:** an **internal load balancer** (not public) or a gateway in front of the DB/Kafka; for stateful sets that need per-broker addresses, per-pod services or the client's bootstrap mechanism.
- **Discovery:** private DNS names (e.g., `db.internal`) rather than IPs, so failover changes DNS, not app config.
- **Security:** mTLS or TLS + auth (DB users, Kafka ACLs), network policies/security groups allowing only the app cluster's egress range, secrets from a vault.
- **Reliability:** connection pooling, timeouts/retries, latency budget (same zone where possible), read replicas, failover plan for the primary, monitoring of the cross-cluster path (latency, errors).
- **Service mesh option:** multi-cluster mesh with east-west gateways and a shared root CA, if both sides run in Kubernetes.
F: Why put data in a separate cluster at all? (Different lifecycle and blast radius, dedicated storage nodes, stricter access, upgrade the app cluster without touching data.)

Q: How would you design multi-tenancy on Kubernetes?
A: It's a spectrum of isolation vs cost:
- **Namespace per tenant (soft):** RBAC per namespace, ResourceQuota + LimitRange, NetworkPolicy default-deny, Pod Security (restricted), separate service accounts, policy engine (Kyverno/OPA) for guardrails. Cheapest; shares the control plane and nodes (noisy neighbours, kernel shared).
- **Dedicated node pools per tenant:** taints/tolerations + node affinity; better performance isolation.
- **Virtual clusters (vcluster) / cluster per tenant:** strongest isolation, own control plane; most cost and operations.
- Pick by trust level (internal teams vs external customers), compliance, and noisy-neighbour risk. Often a mix: shared for small tenants, dedicated for large or regulated ones.
- Also: per-tenant observability and cost showback; tenant-aware SLOs.
F: Which isolation would you use for untrusted customer code? (Separate clusters or sandboxed runtimes like gVisor/Kata, never just namespaces.)

Q: Design monitoring and alerting for 1,000+ edge clusters.
A:
- **Local first:** each site runs a small Prometheus and evaluates its own critical alerts, so monitoring works when the WAN link is down.
- **Central fleet view:** remote-write a small set of fleet metrics (cluster up, node health, key SLIs, versions) to a central Thanos/Mimir; logs shipped with buffering (Fluent Bit) when bandwidth allows.
- **Fleet SLIs:** % of sites healthy, % of sites on the target version, upgrade success rate.
- **Alert routing:** group by site and region so a regional network outage gives one page, not 300; inhibit child alerts.
- **Cardinality control:** strict label budgets; per-site metrics aggregated before sending.
- Heartbeat alert per site (absence of data = site unreachable).
F: A whole region's WAN goes down. How many pages should on-call get? (One, for the region, with the list of sites.)

Q: Estimate: a service gets 10,000 requests/s at peak, each response 20 KB, logs 1 KB per request. How much bandwidth and log storage per day?
A: Show the maths out loud; rough is fine.
- **Bandwidth:** 10,000 × 20 KB = 200 MB/s ≈ **1.6 Gbit/s** at peak.
- **Daily requests:** average maybe 40% of peak → 4,000 req/s × 86,400 s ≈ **350 million requests/day**.
- **Logs:** 350M × 1 KB ≈ **350 GB/day**, about 10 TB/month before compression (logs compress ~5-10x).
- **Pods:** if one pod handles 500 req/s at SLO latency → 20 pods at peak, plus N+1/zone headroom → about 30.
F: How would you cut that log volume by 80%? (Sampling of successful requests, drop debug logs, metrics instead of per-request logs.)

Q: How do you design a service to be operable in production (production readiness review)?
A: A checklist before a service goes live:
- **SLOs** defined and dashboards built; **alerts** on SLO burn with runbooks.
- Health checks (readiness/liveness/startup) that mean something.
- Capacity tested; autoscaling configured; resource requests/limits set.
- Safe deploys: canary/rollback, feature flags; config in Git.
- Dependencies listed with timeouts, retries and fallbacks.
- Backups and tested restore; DR plan.
- Security: secrets management, least privilege, network policies, image scanning.
- On-call ownership and escalation documented.
F: A team wants to launch tomorrow and fails half the checklist. What do you do? (Agree on the must-haves vs follow-ups, launch with a reduced SLO or limited audience, track the rest.)
